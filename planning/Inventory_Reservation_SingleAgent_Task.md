# Inventory Reservation API — Single-Agent Sandboxed Coding Task

## Objective
Build a working inventory reservation REST API — a FastAPI application over
a SQLite-backed stock ledger that lets clients place a time-limited hold on
stock for an order, confirm it into a committed sale, or let it expire back
into available stock — inside one isolated sandbox project folder with its
own `.venv`. **This task must be executed by a single agent, not a
negotiating team.** It has real technical breadth (catalog/stock layer,
reservation/expiry logic, confirm/cancel flow, an internal event log,
reporting) and one genuinely hard correctness problem baked in (concurrent
reservation requests against the same low-stock SKU must never oversell).
Do not split this into multiple roles.

## Constraints
These are hard rules the running agent must not violate:

1. **Single-agent execution.** This task must run as exactly one role
   covering the entire scope below. Do not create a multi-role roster or
   any negotiation between separate agents for this task, regardless of
   how many distinct components it lists below.
2. **Sandbox boundary.** Every file and shell tool call must resolve its
   target path and reject anything that would escape the sandbox root.
3. **Environment isolation.** `run_shell` and `install_package` must always
   execute against the sandbox's own `.venv`, never the AGNIES project's own
   environment.
4. **No overselling, ever.** The total of all currently-active reservations
   plus committed sales for a SKU must never exceed that SKU's total stock,
   even when multiple reservation requests for the same SKU arrive at
   effectively the same time. This must be enforced by the storage layer
   itself (a real transaction/locking strategy), never by application code
   that merely "checks then writes" without protection against a second
   request doing the same check in between.
5. **No fabricated facts or results.** No claim that a reservation
   succeeded, expired, or was correctly rejected under concurrency may be
   made unless it was actually observed by running it — an assumption must
   be labeled as an assumption, not stated as a completed result.
6. **No pre-supplied input data.** No externally-provided fixture file is
   given; the sample catalog/stock data and every simulated concurrent
   request used to demonstrate or test the system must be generated by the
   agent's own code/test setup.
7. **Verified success only.** The task is only complete once its automated
   verification step passes; narrating that the concurrency handling
   "should be safe" does not count as done.

## Baseline Parameters
These two values are exact literal contracts, not illustrative examples —
use these precise numbers unmodified anywhere they're referenced in code,
tests, or config; do not round, scale, or substitute a different value.
- `reservation_ttl_seconds`: 5, unit: seconds, source: ASSUMED (short on
  purpose so the test suite can observe real expiry behavior without
  waiting minutes — a reservation older than this and not yet confirmed
  must be treated as expired).
- `concurrent_request_count`: 20, unit: requests, source: ASSUMED (the
  number of simultaneous reservation requests the test suite must fire at
  a single low-stock SKU to prove the no-overselling constraint).

## Interventions
The technical components needed to satisfy the objective (all owned by the
same single agent — listed separately here only to describe the work, not
to imply separate roles):

- category: catalog, name: A SQLite-backed catalog/stock ledger (under
  `inventory/`) with a schema for SKUs (id, name, total_stock) and a
  reservations table (id, sku, quantity, status [held/confirmed/expired/
  cancelled], created_at, expires_at). The four status values
  (`held`, `confirmed`, `expired`, `cancelled`) are an exact required
  set — these literal strings, unmodified and spelled exactly as given, not
  a renamed/reworded/reordered equivalent (e.g. not "active" for "held").
  Exposes a small Python interface for
  reading a SKU's current available quantity, defined as
  `total_stock - sum(quantity of all held or confirmed reservations for
  that SKU)`.
- category: reservation, name: A reservation function/endpoint that
  atomically checks available quantity and creates a `held` reservation
  only if enough stock is actually available at that instant — the
  check-and-create must happen as one protected operation (e.g. a single
  database transaction with appropriate locking), not as two separate steps
  a second concurrent call could interleave with.
- category: lifecycle, name: Confirm and cancel endpoints that transition a
  `held` reservation to `confirmed` (a committed sale, no longer subject to
  expiry) or `cancelled` (stock immediately available again) — both must
  reject the transition if the reservation is not currently `held` (e.g.
  already expired, already confirmed, or unknown id), returning a correct
  error status rather than silently succeeding.
- category: expiry, name: Expiry handling for reservations older than
  `reservation_ttl_seconds` and still `held` — checked lazily (whenever
  that SKU's availability or that reservation's status is read/acted on),
  not via a background thread/cron — so an expired-but-unread reservation
  is always treated as expired the moment it's touched, freeing its stock
  back to available.
- category: api_layer, name: A FastAPI REST surface: create a SKU, list
  SKUs with current available/held/confirmed breakdown, reserve stock for a
  SKU, confirm a reservation, cancel a reservation — correct HTTP status
  codes for both valid and invalid input (e.g. reserving more than
  available stock, confirming an already-expired reservation).
- category: audit, name: An internal event log (a table, not an external
  webhook) recording every reservation state change (held/confirmed/
  expired/cancelled) with a timestamp, queryable per-SKU, so the eventual
  history of what happened to a given unit of stock is always reconstructable.
- category: testing, name: An automated `pytest` suite that: (1) exercises
  the full reserve → confirm and reserve → cancel lifecycles with correct
  status codes; (2) proves expiry by reserving stock, waiting past
  `reservation_ttl_seconds`, and confirming the stock is available again;
  (3) — the hard part — fires `concurrent_request_count` simultaneous
  reservation requests (via threads or an async client) against a single
  SKU stocked with fewer units than requests, and asserts the number of
  requests that actually succeeded never exceeds that SKU's total_stock,
  proving the no-overselling constraint under real concurrency, not merely
  in a single-threaded call sequence.

## Metrics
- name: test_pass_rate, objective: increase
- name: overselling_incidents, objective: stay_within
- name: sandbox_boundary_violations, objective: stay_within

## Success Criteria
- `inventory/` contains the catalog/stock ledger, reservation logic, and
  expiry handling implementing every behavior described under Interventions
  above.
- The FastAPI REST surface (create SKU, list SKUs, reserve, confirm,
  cancel) returns correct HTTP status codes for both valid and invalid
  input, verified by running it, not narrated.
- The full `pytest` test suite exits with status code 0 when run via
  `run_shell` inside the sandbox's `.venv`, and it demonstrably includes a
  real concurrent-request test against a single low-stock SKU whose
  assertions confirm zero overselling occurred — not a single-threaded
  simulation of concurrency.
- Reservation expiry is demonstrated with a real elapsed-time test (wait
  past `reservation_ttl_seconds`, then verify the stock is available again
  from a fresh read), not asserted from code inspection alone.
- The internal event log contains an entry for every reservation state
  change made during the test run, queryable per-SKU.
- No test, fixture, or demo script reads from an externally supplied input
  file — all SKUs, stock levels, and simulated requests are generated by
  the project's own code.
- No tool call during the task escaped the sandbox root or touched the
  AGNIES project's own environment.
- The task ran as a single agent — no negotiation roster was created for it.
